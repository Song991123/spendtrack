## 1. 프로젝트 개요

### 1-1. 프로젝트명

SpendTrack

### 1-2. 서비스 한 줄 정의

SpendTrack는 쇼핑 주문내역 캡처를 OCR로 분석해 구매 상품 정보를 복원하고, 이를 수입·지출 흐름 안에서 기록, 수정, 조회, 분석할 수 있도록 돕는 가계부형 소비관리 웹앱이다.

### 1-3. 서비스 정체성

SpendTrack는 단순한 OCR 도구도 아니고, 종합 금융관리 서비스도 아니다.  
이 서비스는 `쇼핑 주문내역 OCR`을 차별점으로 삼되, 결과적으로는 `생활형 소비관리`까지 이어지는 구조를 목표로 한다.

| 항목 | 정의 |
| --- | --- |
| 서비스 포지션 | 쇼핑 주문내역 OCR 기반 가계부형 소비관리 서비스 |
| 차별점 | 결제내역이 아닌 실제 구매 상품 맥락 복원 |
| 핵심 사용자 가치 | 기록 장벽 감소, 구매 추적 가능, 소비 흐름 확인 |
| 프로젝트 성격 | 프론트엔드 중심 MVP 구현 |
| 팀 구성 | 2인 팀 프로젝트 |

### 1-4. 프로젝트 배경

기존 카드사, 은행 앱, 간편결제 서비스에서는 결제 내역에 보통 `쿠팡`, `네이버쇼핑`, `11번가` 같은 플랫폼명과 금액 정도만 표시된다.  
이 경우 사용자는 실제로 무엇을 구매했는지, 환불인지, 정기결제인지, 어떤 상품과 관련된 지출인지 추적하기 어렵다.

기존 가계부 앱 역시 수동 입력의 번거로움 때문에 지속 사용이 어렵고, 카드 내역만으로는 상세 맥락을 복원하기 어렵다.

원래 기획은 쇼핑몰 API나 크롤링을 통한 자동 통합을 지향했지만, 세미프로젝트 범위와 보안/구현 현실성을 고려했을 때 직접 연동 중심 접근은 무겁다.  
따라서 SpendTrack는 이를 `OCR 기반 반자동 입력 + 사용자 수정` 방식으로 현실화한다.

## 2. 문제 정의

### 2-1. 핵심 문제

| 문제 | 설명 |
| --- | --- |
| 구매 맥락 부재 | 결제내역에는 플랫폼명과 금액만 보이고 실제 상품 정보는 보이지 않음 |
| 기록 분산 | 쇼핑몰별 주문내역이 흩어져 있어 통합 관리가 어려움 |
| 수동 입력 부담 | 가계부는 직접 기록해야 해서 귀찮고 지속 사용이 어려움 |
| 상태 추적 어려움 | 환불, 취소, 반품, 정기결제를 한눈에 파악하기 어려움 |
| 분석 부족 | 단순 금액 기록만으로는 소비 패턴을 이해하기 어려움 |

### 2-2. 해결 방향

| 해결 방향 | 적용 방식 |
| --- | --- |
| 입력 장벽 완화 | 주문 캡처 OCR |
| 정확도 보완 | OCR 수정 화면 제공 |
| 직접 기록 보완 | 수동 입력 지원 |
| 상품 맥락 복원 | 상품 단위 정보 저장 |
| 생활형 관리 연결 | 내역 조회, 월별 분석, 인사이트 제공 |

## 5. AI 적용 방향

### 5-1. AI 도입 필요성

강사 피드백 기준으로 AI 기능이 포함되면 프로젝트 완성도와 차별성이 높아질 수 있다.  
다만 팀 규모가 2인이고 핵심 기능이 이미 많기 때문에, AI는 `챗봇` 수준이 아니라 `간단한 인사이트 생성 기능` 정도로 제한하는 것이 적절하다.

즉, SpendTrack에서 AI는 별도 대화형 기능이 아니라 `저장된 거래 데이터를 읽고 짧은 분석 메시지를 출력하는 보조 기능`으로 정의한다.

### 5-2. AI 적용 결론

| 항목 | 결정 |
| --- | --- |
| 챗봇 도입 | 제외 |
| 대화형 AI | 제외 |
| 추천 엔진 | 제외 |
| 간단한 소비 인사이트 | 포함 |
| 구현 수준 | 규칙 기반 요약 데이터 + AI 문장화 |

### 5-3. 적용 가능한 AI 방식

#### 방식 A. 규칙 기반 인사이트

가장 안정적이고 구현이 쉬운 방식이다.

예시:
- 이번 달 쿠팡 지출 비중이 가장 높아요.
- 환불 건수가 지난달보다 2건 증가했어요.
- 정기결제로 추정되는 거래가 3건 있어요.
- 식비 관련 지출이 전체의 40%를 차지해요.

장점:
- 구현 난도 낮음
- 데이터 예측 가능
- 시연 안정성 높음
- 프론트엔드 프로젝트 범위에 잘 맞음

단점:
- 엄밀한 의미의 생성형 AI 느낌은 약함

#### 방식 B. 간단한 AI 요약 생성

거래 요약값을 텍스트 프롬프트로 정리한 뒤, 짧은 요약 문장 1~2개를 생성하는 방식이다.

예시 입력:
- 이번 달 총 지출
- 지난달 대비 증감
- 상위 플랫폼
- 상위 카테고리
- 환불 여부
- 정기결제 추정 건수

예시 출력:
- 이번 달은 식비와 온라인 쇼핑 지출 비중이 높고, 특히 쿠팡 사용 빈도가 두드러졌어요.
- 지난달보다 환불 건수가 늘어 전반적인 순지출은 다소 줄어든 상태예요.

장점:
- 발표 시 AI 느낌이 더 잘 남음
- 강사 피드백에 대응하기 좋음

단점:
- 외부 API 사용 여부 결정 필요
- 비용/키 관리/네트워크 이슈가 생길 수 있음

### 5-4. 최종 결정

이번 프로젝트에서는 `방식 B. 규칙 기반 요약 데이터 + AI 문장화`를 최종안으로 채택한다.

| 결정안 | 이유 |
| --- | --- |
| 규칙 기반 요약 데이터 + AI 문장화 | AI를 실제 사용하면서도 분석 로직을 통제할 수 있고, 챗봇보다 범위가 훨씬 작음 |

적용 방식은 아래와 같다.

1. 프론트엔드에서 월별 거래 데이터를 요약한다.
2. 총 지출, 총 수입, 상위 플랫폼, 환불 건수, 정기결제 추정 건수 등의 핵심 값을 정리한다.
3. Firebase Cloud Functions를 통해 외부 LLM API를 호출한다.
4. AI는 전달받은 요약값을 바탕으로 1~2문장의 소비 인사이트 메시지를 생성한다.
5. 생성된 메시지는 Home 또는 Analysis 화면에서 카드 형태로 노출한다.

즉, 분석 로직 전체를 AI에게 맡기지 않고, `서비스가 만든 구조화 데이터`를 `AI가 자연어 메시지로 정리하는 역할`만 수행하도록 제한한다.

이 방식은 다음 장점을 가진다.

- 챗봇보다 구현 범위가 작다.
- 결과 형식을 통제하기 쉽다.
- 발표 시 AI 기능을 설명하기 좋다.
- 규칙 기반만 사용할 때보다 자연스러운 문장을 만들 수 있다.
- 핵심 기능 구현을 방해하지 않는 선에서 확장 가능하다.

### 5-5. 인사이트 예시 문구

| 유형 | 예시 |
| --- | --- |
| 지출 비중 | 이번 달은 온라인 쇼핑 지출 비중이 높아요. |
| 반복 지출 | 정기결제로 추정되는 거래가 3건 있어요. |
| 플랫폼 편중 | 쿠팡 비중이 가장 높고, 네이버쇼핑은 지난달보다 줄었어요. |
| 환불/취소 | 환불 건수가 늘어 실제 순지출은 예상보다 낮아요. |
| 소비 조언 | 비슷한 상품군 반복 구매가 보여요. 불필요한 중복 소비인지 확인해보세요. |

### 5-6. AI 기술 적용 방식

현재 프로젝트는 별도 백엔드 서버 없이 Firebase 중심 구조를 사용하므로, AI 기능은 아래 구조로 도입한다.

| 구성 요소 | 역할 |
| --- | --- |
| React 프론트엔드 | 거래 데이터를 집계하고 요약값 생성 |
| Firebase Firestore | 거래 데이터 저장 |
| Firebase Cloud Functions | AI API 호출용 얇은 서버 역할 |
| 외부 LLM API | 요약 데이터를 자연어 소비 인사이트로 변환 |

권장 처리 흐름:

1. 사용자의 거래 데이터가 Firestore에 저장된다.
2. 프론트엔드 또는 분석 로직이 월별 요약값을 만든다.
3. 요약값만 Cloud Functions로 보낸다.
4. Cloud Functions에서 API 키를 사용해 LLM API를 호출한다.
5. 결과 문장을 받아 화면에 출력하거나 Firestore에 저장한다.

보안 정책:

- API 키는 프론트엔드에 직접 두지 않는다.
- AI 호출은 반드시 Cloud Functions를 통해 처리한다.
- AI는 원본 전체 기록보다 요약값만 받는 구조를 우선한다.

이로써 별도 백엔드 없이도 AI 기능을 안전하게 추가할 수 있다.

| 수정 | OcrEdit | OCR 결과 보정 및 저장 |
| 조회 | Transactions | 수입·지출 내역 조회 |
| 분석 | Analysis | 소비 흐름 분석 |

### 8-2. 구조 원칙

- 한 화면에 여러 흐름을 몰아넣지 않는다.
- `입력 방식 선택`, `OCR 입력`, `수동 입력`, `OCR 수정`을 분리한다.
- OCR은 자동화 주 흐름, 수동 입력은 보조이지만 독립적인 흐름으로 유지한다.
- Home은 허브, Analysis는 깊은 분석으로 역할을 분리한다.

## 14. 기존 기획 자료 재활용 가이드

기존 중간/기말 기획 자료는 최대한 재활용하되, SpendTrack 방향에 맞게 아래와 같이 수정한다.

### 14-1. 재활용 우선순위

| 기존 자료 | 재활용 여부 | SpendTrack용 변경 방향 |
| --- | --- | --- |
| 문제 정의 | 적극 재사용 | 카드 내역만으로는 상품 추적이 어렵다는 문제 유지 |
| 경쟁사 SWOT | 요약 재사용 | 토스/뱅크샐러드/편한가계부 대비 상품 맥락 복원 강조 |
| 포지셔닝 맵 | 재사용 가능 | 자동화 vs 수동, 맥락 풍부함 vs 단순 금액 중심으로 축 수정 |
| 메인 사용자/페르소나 | 재사용 가능 | 온라인 쇼핑 빈도와 기록 귀찮음을 더 강조 |
| 저니맵 | 재사용 가능 | 앱 설치/연동 중심에서 입력-수정-저장-조회 흐름 중심으로 수정 |
| 정보 아키텍처 | 부분 재사용 | 홈/구매내역/분석 구조 유지, 카드관리는 거래내역 개념으로 재해석 |
| 서비스 주요 기능 | 부분 재사용 | 자동 연동은 OCR 기반 반자동으로 치환 |

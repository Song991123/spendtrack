# SpendTrack 1차 중간 발표 v2 — 슬라이드 가이드

작성일: 2026-04-21
대상 파일: `SpendTrack_중간발표_v2.pptx` (전체 17 페이지 · 표지 + 15 본문 + 마무리)

v1 대비 변경: 시장 조사 / 경쟁자 해상도 비교 / 포지셔닝 맵 / 페르소나 / 사용자 플로우 / 기능명세 / IA / 기술 선정 이유 / 로드맵·리스크 / 협업 일정 섹션을 보강하여, "기획 과정을 요약해서 발표한다" 라는 1차 중간 발표 성격에 맞게 볼륨을 늘렸습니다.

v2-rev 에서는 (1) 금융위 마이데이터 2.0 공식 문구와 국내 이커머스·간편결제 시장 점유율을 근거로 추가하고, (2) 토스·뱅크샐러드·편한가계부 등 경쟁 서비스의 해상도 한계를 직접 비교하는 슬라이드를 신설했습니다. (3) 리팩토링 결과 반영 — components 9 카테고리 분리, pages 3단 구조, CSV 다중 플랫폼 정규화와 인코딩 자동 감지를 IA·기술 스택·구현 범위 슬라이드에 반영했습니다.

## 2. 슬라이드별 핵심 문장 · 발표 멘트 · 이미지/비주얼

### 슬라이드 1 — 표지
핵심 문장: "쇼핑 주문내역 OCR 기반 소비관리 서비스 — React Publisher v1"
발표 멘트: "안녕하세요. 오늘은 SpendTrack 1차 중간 발표입니다. 현재 단계는 실연동 이전의 React 퍼블리셔 v1 이고, 오늘은 기획·설계·화면 구조를 중심으로 말씀드리겠습니다."
비주얼: 중앙 세로 정렬된 프로덕트 이름 + 좌측 오렌지 세로 바 + 발표자 정보. 아이콘 없음 (표지 밀도 낮게).

### 슬라이드 2 — 프로젝트 소개
핵심 문장: "주문 이미지·카드내역·수동 입력을 하나의 거래 스토어로 합치는 소비관리 서비스"
발표 멘트: "SpendTrack 은 카드사 내역만으로는 '무엇을 샀는지' 가 빠진다는 문제에서 출발했습니다. 저희는 주문 캡처 이미지, 카드 CSV, 수동 입력을 하나의 거래 스토어로 합치는 퍼블리셔를 먼저 완성했습니다."
비주얼: 한 줄 정의 + 3개 정체성 카드 (서비스 포지션 / 핵심 사용자 가치 / 프로젝트 성격).

### 슬라이드 3 — 문제 인식
핵심 문장: "카드·간편결제는 금액은 보이지만, 금융위 공식 문구에서도 '물품내역' 은 비어 있다."
발표 멘트: "기존 가계부 앱은 대부분 카드사 내역만 보여주기 때문에, 정작 무엇을 샀는지가 비어 있습니다. 단순한 체감이 아니라, 금융위가 마이데이터 2.0 문서에서 '카드·간편결제 거래내역에는 물품내역이 제공되지 않는다' 라고 공식적으로 명시해 둔 부분입니다. SpendTrack 은 이 공백을 OCR 기반 반자동 입력과 사용자 보정 UI 로 메웁니다."
비주얼: 상단 인용 chip + 3개 문제 카드(구매 맥락 부재·기록 분산·수동 입력 부담) + 중간 정책 근거 chip (금융위 마이데이터 2.0 인용) + 하단 결론 다크 바.

### 슬라이드 4 — 시장 조사 · 반입 경로
핵심 문장: "국내에서 상품 맥락을 합법적으로 반입할 경로는 구조적으로 제한되며, OCR 만이 사실상 유일하다."
발표 멘트: "상품 맥락을 가져올 수 있는 반입 경로를 하나씩 검증했습니다. 쇼핑몰 공식 API 는 판매자 전용만 공개되어 있고, CODEF·오픈뱅킹은 결제처·금액까지만 내려옵니다. 마이데이터는 지정 사업자만 접근 가능하고, 크롤링은 이용약관 위반이자 2FA·캡차 때문에 유지비용이 큽니다. 남는 건 주문 캡처 OCR 뿐인데, 정확도 한계는 사용자 보정 UI 로 해결한다는 설계입니다. 이 문제의 스케일은 작지 않습니다 — 쿠팡·네이버 이커머스 점유율 합이 약 43%, 간편결제는 네이버페이 한 곳이 51.5% 를 차지합니다."
비주얼: 7행 비교 표(반입 경로 / 접근 가능성 / 한계, 마지막 행 OCR 강조) + 하단 '블라인드 규모' chip(시장 점유율) + 보라색 결론 라인.

### 슬라이드 5 — 경쟁 서비스의 해상도 한계
핵심 문장: "경쟁 서비스들의 해상도 상한은 '카테고리' 에서 멈춘다 — 상품 단위는 사용자가 직접 적어왔다."
발표 멘트: "기존 앱들이 어디까지 보여주는지 비교해 봤습니다. 토스는 간편결제·카드 내역을 통합해서 보여주지만 결제처와 금액까지만 입니다. 뱅크샐러드는 자동 가계부로 카테고리 자동 분류까지 해 주지만 품목 단위 조회는 지원하지 않습니다. 편한가계부는 문자 파싱 기반이라 상품명은 사용자가 직접 써야 합니다. 이 해상도 상한은 명확하고, 그래서 사용자들이 직접 쿠팡·네이버 주문목록을 엑셀로 옮겨 적거나 Chrome 확장을 만들어 쓰는 자력구제가 꾸준히 관측됩니다. SpendTrack 의 빈 자리는 이 지점입니다."
비주얼: 4장 카드(토스 / 뱅크샐러드 / 편한가계부 / SpendTrack) — 각 카드에 이름·포지션·해상도·한계(또는 차별점) 표시. 마지막 SpendTrack 카드만 다크 + 시안 강조. 하단 '수요 신호' chip + 결론 다크 바.

### 슬라이드 6 — 포지셔닝 맵
핵심 문장: "자동화 × 상품 세분화 2축에서 SpendTrack 은 우상단을 목표로 한다."
발표 멘트: "이 맵은 가로축이 '입력 자동화', 세로축이 '기록되는 정보의 깊이' 입니다. 기존 가계부는 좌하단, 카드·페이 내역은 우하단, 쇼핑몰 자체 주문내역은 좌상단입니다. SpendTrack 은 'OCR+CSV 로 반자동 + 상품 레벨 기록' 이라는 우상단 영역을 노립니다."
비주얼: 4사분면 맵, 경쟁군 점(수기 가계부·카드/페이·자동 가계부·쇼핑몰) + SpendTrack 강조 점(점선 링) + 우측 다크 설명 박스.

### 슬라이드 7 — 페르소나
핵심 문장: "20-40대 직장인 / 신혼부부. 쇼핑은 많지만 분석은 포기."
발표 멘트: "두 개의 주요 페르소나를 잡았습니다. 첫째, 온라인 쇼핑을 주로 하는 직장인. 카드 앱은 쓰지만 내역이 추상적이라 분석은 포기하는 사용자. 둘째, 가계부를 함께 쓰고 싶은 신혼·기혼 생활비 관리 사용자. 공유 분석이 필요하지만 입력 부담으로 유지가 안 되는 사용자."
비주얼: 좌·우 2장 페르소나 카드 (아이콘/타입/제목/니즈/불편/기대). 메인 페르소나는 다크, 서브는 라이트.

### 슬라이드 8 — 서비스 목표 & 차별점
핵심 문장: "입력 3가지(OCR/CSV/수동) + 병합 UX = SpendTrack 의 정체성."
발표 멘트: "저희의 차별점은 두 개입니다. 첫째, 입력 경로가 3개라는 점. 어떤 기록 습관을 가진 사용자든 유입될 수 있습니다. 둘째, 같은 거래가 여러 경로로 들어왔을 때 사용자가 직접 '같은 거래로 병합할 것인가' 를 선택하게 한 점. 자동 매칭 오류를 감수하지 않습니다."
비주얼: 좌 5개 서비스 목표 카드(아이콘 + 한 줄), 우 다크 '핵심 차별점' 박스 + 4개 bullet.

### 슬라이드 9 — 사용자 플로우 (3-Phase)
핵심 문장: "Phase1 진입 → Phase2 입력 3경로 → Phase3 병합·저장·조회."
발표 멘트: "사용자 플로우는 3 페이즈로 깔끔하게 나뉩니다. Phase 1 은 로그인 → 홈 → 입력 선택 허브까지. Phase 2 에서 OCR / CSV / 수동 입력 중 하나로 분기하고, OCR 은 분석 결과를 편집하는 하위 단계를 거칩니다. Phase 3 에서는 기존 거래와의 병합 여부를 사용자에게 물어본 뒤 스토어에 저장하고, 바로 거래·분석 화면으로 연결됩니다."
비주얼: 상단 수평 3 스텝(공통) → 중단 수평 3 카드(3 입력 경로, OCR 카드는 오른쪽으로 OCR Edit 꼬리) → 하단 병합 모달 → localStorage 스토어 → 거래/분석. 3 phase 단위로 구분선.

### 슬라이드 10 — 기능 명세 (F-01 ~ F-13)
핵심 문장: "13개 기능을 필수 · 포함 · 선택 3단계 우선도로 관리."
발표 멘트: "기능은 F-01 부터 F-13 까지 13개로 구성되어 있고, 필수 / 포함 / 선택 세 단계의 우선도를 가집니다. v1 퍼블리셔에는 필수 10개와 '포함' 으로 분류된 인사이트 메시지 UI 까지 포함되어 있고, 'F-13 상품명 기반 검색 링크' 만 선택 항목으로 두었습니다."
비주얼: 4열 테이블 (ID / 기능명 / 설명 / 우선도). 우선도 컬럼은 색 강조.

### 슬라이드 11 — 화면 구조 (IA)
핵심 문장: "라우트 6군 · 11개 · 컴포넌트 9 카테고리 · pages 3단 구조."
발표 멘트: "화면 구조는 인증 / 허브 / 입력 / 편집 / 조회·분석 / 설정 의 6개 기능군으로 정리했고, 총 11개 라우트입니다. 입력 기능군이 가장 두껍습니다. 리팩토링 과정에서 components 는 primitives / layout / form / list / modal / display / composite / charts / auth 의 9 카테고리로 분리했고, pages 는 각 화면 폴더가 `index.tsx` + `components/` + `data.ts` 의 3단 구조로 고정되어 있습니다. 실연동 단계에서 기능군 단위로 오너십을 쪼갤 수 있도록 설계했습니다."
비주얼: 상단 라우트 섹션(6개 기능군 × 라우트 칩) + 하단 components 9 카테고리 chip 행 + 우측 상단 pages 3단 구조 라벨.

### 슬라이드 12 — 기술 스택 & 선정 이유
핵심 문장: "각 기술은 '2인 규모 · 차기 실연동 교체 용이' 라는 공통 기준으로 선택되었습니다."
발표 멘트: "React 19 와 TypeScript 는 도메인 타입(거래·상품·플랫폼)을 명시해 협업 오류를 줄이기 위함. Vite 는 HMR 과 빠른 빌드로 세미프로젝트 DX 에 유리. Router 는 HashRouter 기반 정적 호스팅과 깊은 링크 안정성. styled-components 는 디자인 토큰과 궁합이 좋아 선택. Recharts 는 React 선언형 차트라 Home/Analysis 에 바로 붙일 수 있었습니다. 마지막 카드의 localStorage 기반 스토어와 CSV 정규화는 v2-rev 에서 강조된 부분인데, 쿠팡·네이버·무신사 3 플랫폼의 CSV 헤더를 자동 매핑하고 BOM + UTF-8/EUC-KR 인코딩을 자동 감지합니다. 공개 API 는 추후 Firestore 로 교체하기 쉽도록 단순하게 유지했습니다."
비주얼: 2열 × 3행 기술 카드 (아이콘 + 이름 + 선정 이유). 마지막 카드는 CSV 정규화 + 인코딩 감지까지 서술.

### 슬라이드 13 — 현재 구현 범위
